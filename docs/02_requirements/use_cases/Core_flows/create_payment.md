# UC-001: Create Payment

## 1. Overview

This use case describes how a Merchant creates a new `Payment` in the Payment Orchestration Platform.

Creating a Payment represents the merchant's intent to collect money from an end customer.

At this stage, the system may either:

- create only the Payment entity
- create the Payment and immediately start processing
- create the Payment and wait for explicit confirmation

**Core principle:**

> Create Payment = create payment intent, not necessarily execute payment immediately

---

## 2. Goal

Allow Merchant to create a Payment in a safe, idempotent, auditable, and production-ready way.

The system must:

- validate request data
- authenticate and authorize Merchant
- enforce Merchant configuration
- prevent duplicate payments
- create a persistent Payment entity
- create an idempotency record atomically
- prepare the Payment for further processing
- publish an internal event after successful persistence

---

## 3. Actors

| Actor                          | Description                                            |
| ------------------------------ | ------------------------------------------------------ |
| Merchant System                | External client creating the payment                   |
| Payment API                    | Public API receiving the request                       |
| Payment Service                | Internal service responsible for Payment creation      |
| Idempotency Store              | Component preventing duplicate operations              |
| Merchant Configuration Service | Component providing merchant-specific rules and limits |
| Event Bus                      | Internal async communication layer                     |
| Observability Platform         | Logging, metrics, tracing, and alerting stack          |

---

## 4. Preconditions

Before Payment creation:

- Merchant exists in the system
- Merchant status is `ACTIVE`
- Merchant API credentials are valid
- Merchant is authorized to create payments
- Requested currency is supported by Merchant configuration
- Requested payment method is supported by Merchant configuration
- Amount is valid and within configured limits
- Idempotency key is provided
- API version is supported
- Request does not exceed rate limits

---

## 5. Trigger

Merchant sends `Create Payment` request to the platform API.

Example trigger:

`POST /payments`

---

## 6. Input Data

| Field           | Required    | Description                                              |
| --------------- | ----------- | -------------------------------------------------------- |
| merchant_id     | Yes         | Merchant identifier                                      |
| amount          | Yes         | Payment amount                                           |
| currency        | Yes         | ISO 4217 currency code                                   |
| payment_method  | Yes         | Requested payment method                                 |
| order_id        | Yes         | Merchant-side order reference                            |
| customer_id     | Optional    | Merchant-side customer reference                         |
| return_url      | Conditional | Required for redirect / 3DS flows                        |
| metadata        | Optional    | Additional merchant data                                 |
| processing_mode | Optional    | Defines whether processing starts immediately            |
| idempotency_key | Yes         | Unique request key scoped per Merchant                   |
| correlation_id  | Optional    | Request trace identifier. Generated by system if missing |

---

## 7. Processing Mode

The system must support different payment creation modes.

| Mode           | Description                                                      |
| -------------- | ---------------------------------------------------------------- |
| CREATE_ONLY    | Only Payment is created. Processing does not start automatically |
| AUTO_PROCESS   | Payment is created and processing starts immediately             |
| MANUAL_CONFIRM | Payment is created and waits for explicit confirmation           |

Default mode:

`AUTO_PROCESS`

### Rules

- `CREATE_ONLY` must not create Payment Attempt
- `AUTO_PROCESS` may trigger Payment Attempt creation after Payment persistence
- `MANUAL_CONFIRM` requires a separate confirmation action before processing
- Processing mode must be stored as part of Payment creation context

---

## 8. Main Success Flow

1. Merchant sends `Create Payment` request.
2. Payment API validates API version.
3. Payment API authenticates Merchant.
4. Payment API checks Merchant authorization.
5. System validates request schema.
6. System checks rate limits.
7. System validates idempotency key.
8. System checks whether the idempotency key was already used.
9. System loads Merchant configuration.
10. System validates Merchant status.
11. System validates amount, currency, payment method, and processing mode.
12. System creates `Payment` entity.
13. System creates idempotency record.
14. System stores request hash, response template, and creation context.
15. System commits Payment and idempotency record atomically.
16. System publishes `PaymentCreated` event.
17. If `processing_mode = AUTO_PROCESS`, system schedules payment processing.
18. System returns Payment response to Merchant.

---

## 9. Resulting State

After successful creation:

| Entity             | Result                                            |
| ------------------ | ------------------------------------------------- |
| Payment            | Created                                           |
| Payment Attempt    | Not created yet, unless `AUTO_PROCESS` is enabled |
| Routing Decision   | Not created yet                                   |
| Transaction        | Not created yet                                   |
| Idempotency Record | Created                                           |
| Event              | `PaymentCreated` published                        |

Default Payment status:

`CREATED`

If `AUTO_PROCESS` is enabled, Payment may transition asynchronously to:

`PROCESSING`

---

## 10. Alternative Flows

### 10.1 Duplicate Idempotency Key With Same Payload

If the same idempotency key is received again with the same payload:

- system must not create a new Payment
- system must return the original response
- no duplicate events must be published

Result:

`200 OK`

---

### 10.2 Duplicate Idempotency Key With Different Payload

If the same idempotency key is received with a different payload:

- system must reject the request
- no new Payment is created
- conflict must be logged

Result:

`409 Conflict`

---

### 10.3 Missing Idempotency Key

If idempotency key is missing:

- request is rejected
- no Payment is created

Result:

`400 Bad Request`

---

### 10.4 Invalid Merchant Credentials

If credentials are invalid:

- request is rejected
- no Payment is created

Result:

`401 Unauthorized`

---

### 10.5 Merchant Not Authorized

If Merchant is authenticated but not allowed to perform the operation:

- request is rejected
- no Payment is created

Result:

`403 Forbidden`

---

### 10.6 Merchant Not Active

If Merchant status is not `ACTIVE`:

- request is rejected
- no Payment is created

Result:

`403 Forbidden`

---

### 10.7 Unsupported Currency

If currency is not supported by Merchant configuration:

- request is rejected
- no Payment is created

Result:

`422 Unprocessable Entity`

---

### 10.8 Unsupported Payment Method

If payment method is not enabled for Merchant:

- request is rejected
- no Payment is created

Result:

`422 Unprocessable Entity`

---

### 10.9 Invalid Amount

If amount is zero, negative, below minimum, or above maximum configured limit:

- request is rejected
- no Payment is created

Result:

`422 Unprocessable Entity`

---

### 10.10 Rate Limit Exceeded

If Merchant exceeds configured rate limits:

- request is rejected
- no Payment is created
- retry guidance may be returned

Result:

`429 Too Many Requests`

---

### 10.11 Unsupported API Version

If API version is not supported:

- request is rejected
- no Payment is created

Result:

`400 Bad Request`

---

### 10.12 Event Bus Unavailable

If Payment and idempotency record are persisted but event bus is temporarily unavailable:

- Payment creation remains successful
- event must be retried using reliable publishing mechanism
- Merchant receives successful response

Result:

`201 Created`

## 12. Merchant Configuration Impact

The system must apply Merchant-specific configuration during Payment creation.

Configuration may define:

- allowed payment methods
- supported currencies
- minimum and maximum amount limits
- default processing mode
- retry limits
- routing strategy
- antifraud requirements
- webhook configuration
- rate limits

### Rules

- Merchant configuration must be loaded before Payment validation is completed
- Request values must be validated against Merchant configuration
- Invalid method / currency / amount combinations must be rejected before Payment creation
- Configuration snapshot or version must be stored in Payment context for auditability

---

## 13. Idempotency Rules

The system must enforce idempotency at Payment creation level.

### Rules

- `idempotency_key` must be unique per Merchant
- same key + same payload returns original result
- same key + different payload must be rejected
- idempotency key must have configurable retention period
- expired idempotency keys must not be silently reused
- suspicious replay patterns must be detectable

### Idempotency Record Must Store

| Field            | Description                        |
| ---------------- | ---------------------------------- |
| merchant_id      | Merchant scope                     |
| idempotency_key  | Client-provided key                |
| request_hash     | Hash of normalized request payload |
| payment_id       | Created Payment reference          |
| response_payload | Original response                  |
| status           | CREATED / COMPLETED / FAILED       |
| created_at       | Creation timestamp                 |
| expires_at       | Expiration timestamp               |

### Business Value

Idempotency prevents:

- duplicate charges
- duplicate orders
- inconsistent payment state
- merchant-side retry failures
- double processing caused by network timeouts

---

## 14. Consistency & Transaction Boundary

Payment creation must be strongly consistent.

The following operations must be committed atomically:

- Payment entity creation
- idempotency record creation
- request hash persistence
- initial response persistence

### Rules

- Payment must not exist without related idempotency record
- idempotency record must not point to missing Payment
- if atomic commit fails, request must be treated as failed
- event publication must happen only after successful persistence

Recommended implementation pattern:

- transactional database write
- outbox pattern for reliable event publication

## 19. Acceptance Criteria

### AC-001: Successful Payment Creation

Given Merchant is active  
And request data is valid  
And idempotency key is unique  
When Merchant sends Create Payment request  
Then system creates Payment  
And creates idempotency record  
And returns Payment ID  
And Payment status is `CREATED`

---

### AC-002: Duplicate Request Handling

Given Payment was already created with idempotency key  
When Merchant repeats the same request with the same key and same payload  
Then system returns original Payment response  
And does not create duplicate Payment  
And does not publish duplicate `PaymentCreated` event

---

### AC-003: Idempotency Payload Mismatch

Given idempotency key was already used  
When Merchant sends a different payload with the same key  
Then system rejects the request  
And no new Payment is created  
And response status is `409 Conflict`

---

### AC-004: Unsupported Currency

Given currency is not supported for Merchant  
When Merchant sends Create Payment request  
Then system rejects request  
And returns validation error  
And no Payment is created

---

### AC-005: Inactive Merchant

Given Merchant status is not `ACTIVE`  
When Merchant sends Create Payment request  
Then system rejects request  
And no Payment is created

---

### AC-006: Processing Mode CREATE_ONLY

Given request contains `processing_mode = CREATE_ONLY`  
When Payment is created  
Then no Payment Attempt is created automatically  
And Payment status remains `CREATED`

---

### AC-007: Processing Mode AUTO_PROCESS

Given request contains `processing_mode = AUTO_PROCESS`  
When Payment is created  
Then system publishes `PaymentProcessingRequested`  
And payment processing may start asynchronously

---

### AC-008: Rate Limit Exceeded

Given Merchant exceeds configured rate limit  
When Merchant sends Create Payment request  
Then system rejects request  
And response status is `429 Too Many Requests`  
And no Payment is created

---

### AC-009: Atomic Persistence

Given database failure occurs during Payment creation  
When atomic commit fails  
Then neither Payment nor idempotency record is persisted  
And Merchant receives error response

---

### AC-010: Event Publishing Failure

Given Payment and idempotency record are successfully persisted  
And Event Bus is temporarily unavailable  
When event publication fails  
Then Payment creation remains successful  
And event publication is retried via reliable mechanism

---

## 20. Edge Cases

| Case                                      | Expected Behavior                                            |
| ----------------------------------------- | ------------------------------------------------------------ |
| API timeout after Payment creation        | Retry with same idempotency key returns original response    |
| Duplicate request from Merchant           | Original response is returned                                |
| Missing idempotency key                   | Request is rejected                                          |
| Same key with different payload           | Request is rejected                                          |
| Unsupported method / currency combination | Request is rejected                                          |
| Event bus unavailable after persistence   | Payment creation succeeds, event retry is scheduled          |
| Database failure before commit            | No Payment and no idempotency record are persisted           |
| Merchant config changes during request    | System uses consistent config snapshot/version               |
| Missing correlation_id                    | System generates one                                         |
| Expired idempotency key reused            | Request is rejected or treated according to retention policy |

## 21. Design Decisions

### Payment Creation Does Not Require PSP Call

**Why:**

- reduces latency
- improves reliability
- separates intent creation from execution
- supports async-first architecture

---

### Mandatory Idempotency

**Why:**

- prevents duplicate payments
- makes client retries safe
- supports distributed failure handling

---

### Strong Consistency for Payment Creation

**Why:**

- duplicate prevention requires strict guarantees
- Payment ID must be created exactly once
- Payment and idempotency record must never diverge

---

### Outbox Pattern for Event Publication

**Why:**

- prevents lost events
- avoids publishing events before database commit
- supports reliable async processing

---

### Processing Mode Support

**Why:**

- supports different merchant integration models
- enables immediate and delayed execution flows
- improves flexibility without changing API contract

---

### API Versioning

**Why:**

- allows safe API evolution
- protects existing merchant integrations
- enables gradual migration

---

## 22. Summary

`Create Payment` is the entry point into the payment lifecycle.

It must be:

- idempotent
- auditable
- strongly consistent
- traceable
- independent from PSP execution
- safe for retries and partial failures

This allows the platform to support:

- async processing
- retries
- failover
- multi-PSP orchestration
- enterprise-grade merchant integrations
